# 감정 일기 — React + Supabase (`26-w09-diary`)

> 이 README는 실습을 완성한 뒤, 배포 직전 단계에서 작성한 프로젝트 설명서입니다.  
> 자세한 실습 절차는 [`guide.md`](./guide.md)를 참고하세요.

## 소개

이 프로젝트는 하루 동안 느낀 감정과 생각을 기록하고 관리할 수 있는 웹 기반 감정 일기장입니다.

사용자는 기쁨, 평온, 슬픔, 화남, 불안의 다섯 가지 감정 중 하나를 선택하고, textarea에 자신의 하루와 생각을 자유롭게 작성할 수 있습니다.

작성한 일기는 Supabase 데이터베이스에 저장되며, 저장된 일기를 최신순으로 확인하거나 감정별로 분류해서 볼 수 있습니다. 또한 필요하지 않은 일기는 삭제할 수 있습니다.

주요 기능은 다음과 같습니다.

- 5가지 감정 선택 및 일기 작성
- Supabase 데이터베이스를 이용한 일기 저장
- 작성한 일기 최신순 조회
- 감정별 필터링 기능
- 일기 삭제 기능
- 로딩, 저장 중, 빈 목록 및 오류 상태 표시
- PC와 스마트폰에 대응하는 반응형 화면

## 어떻게 만들었나요

먼저 Copilot의 Plan 모드를 활용해 감정 일기 웹앱의 목적과 필요한 기능을 정리하고, 데이터베이스 구조와 화면 구성, 구현해야 할 기능을 계획했습니다.

이후 Agent 모드에서 계획을 바탕으로 기존 Vite + React 프로젝트에 필요한 코드를 적용하는 방식으로 개발을 진행했습니다.

개발은 다음과 같은 순서로 진행했습니다.

1. **프로젝트 구조 확인:** 기존 Vite + React 프로젝트를 확인하고 필요한 파일과 폴더를 정리했습니다.
2. **스타일 설정:** Tailwind CSS를 설치하고 반응형 디자인을 적용했습니다.
3. **Supabase 연결:** `src/lib/supabase.js`에서 Supabase 클라이언트를 초기화하도록 구성했습니다.
4. **데이터 처리:** `src/api/diaries.js`에 일기 조회, 추가, 삭제 함수를 분리했습니다.
5. **화면 구현:** `src/App.jsx`에서 감정 선택, 일기 작성, 목록 출력, 필터링 및 삭제 기능을 구현했습니다.
6. **오류 및 상태 처리:** 데이터를 불러오는 중이거나 저장하는 중일 때의 표시, 빈 목록 안내와 오류 메시지를 추가했습니다.
7. **테스트:** 일기를 작성하고 삭제한 뒤 새로고침했을 때에도 데이터가 유지되는지 확인하는 방식으로 기능을 점검했습니다.

데이터 처리는 Supabase의 기본 CRUD 기능을 사용했으며, Realtime 웹소켓 구독 대신 작성이나 삭제가 완료되면 목록을 다시 조회하는 방식으로 구현했습니다.

## 데이터는 어디에 저장되나요

이 프로젝트의 일기 데이터는 Supabase의 `diaries` 테이블에 저장됩니다.

테이블은 다음과 같은 구조로 구성되어 있습니다.

| 컬럼 | 자료형 | 설명 |
|---|---|---|
| `id` | bigint | 일기 고유 번호, 자동 생성 |
| `content` | text | 일기 본문 |
| `emotion` | text | 선택한 감정 |
| `created_at` | timestamptz | 작성 일시, 기본값 자동 생성 |

감정 데이터는 다음 다섯 가지 값으로 저장됩니다.

- `joy`: 기쁨
- `calm`: 평온
- `sad`: 슬픔
- `angry`: 화남
- `anxious`: 불안

8주차에 만들었던 To-Do 앱은 `localStorage`를 이용해 브라우저 내부에 데이터를 저장하는 방식이었습니다. 따라서 다른 기기나 브라우저에서는 기존 데이터가 자동으로 공유되지 않았습니다.

반면 이번 프로젝트는 Supabase라는 외부 데이터베이스를 사용합니다. 데이터가 브라우저 내부가 아닌 서버 측 데이터베이스에 저장되므로 같은 Supabase 프로젝트에 연결된 웹앱이라면 PC와 스마트폰, 서로 다른 브라우저에서도 동일한 일기 데이터를 확인할 수 있습니다.

다만 현재 프로젝트에는 사용자 로그인이나 개인별 데이터 구분 기능이 없습니다. 따라서 접속하는 사용자 모두가 동일한 일기 데이터를 공유하는 구조입니다.

## 보안에서 확인한 것 (사이버보안과 체크포인트)

이번 프로젝트를 진행하면서 데이터베이스 연결뿐 아니라 API 키와 데이터 접근 권한 관리의 중요성도 확인했습니다.

### 1. Supabase 키 관리

Supabase 연결에 필요한 URL과 Publishable Key는 프로젝트 최상위 폴더의 `.env.local` 파일에 저장했습니다.

환경변수 이름은 다음과 같습니다.

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

`.env.local`은 GitHub에 업로드하지 않도록 `.gitignore`에 등록해야 합니다. 소스 코드 저장소에 접속 정보가 그대로 노출되는 것을 방지하기 위해서입니다.

또한 Supabase의 Publishable Key는 브라우저에서 사용하는 공개용 키이므로 비밀번호나 Service Role Key처럼 비밀로 취급하는 서버 전용 키와는 다릅니다.

### 2. 브라우저 개발자 도구에서 키 확인

브라우저의 개발자 도구 Network 탭이나 배포된 JavaScript 파일을 확인하면 Supabase URL과 Publishable Key가 노출될 수 있습니다.

이는 Vite의 `VITE_` 환경변수가 브라우저에서 실행되는 코드에 포함되기 때문입니다.

따라서 환경변수 파일에 키를 저장했다는 사실만으로 데이터가 완전히 보호되는 것은 아닙니다.

실제로 데이터를 보호하는 중요한 수단은 Supabase의 RLS(Row Level Security) 정책입니다. RLS는 데이터베이스에 접근할 수 있는 사용자가 어떤 데이터를 조회하거나 추가하고 삭제할 수 있는지 제한하는 보안 기능입니다.

### 3. RLS 정책의 한계와 위험성

현재 설정된 `using (true)` 정책은 해당 정책이 적용되는 작업에 대해 모든 대상 행을 허용한다는 의미입니다. 추가 작업에 `with check (true)`가 적용되어 있다면 삽입 데이터도 별도 조건 없이 허용됩니다.

이러한 설정은 실습 과정에서 데이터 CRUD 기능을 간단히 확인하기에는 편리하지만 실제 서비스에 사용하기에는 보안상 위험이 있습니다.

현재 프로젝트에는 사용자 인증 기능과 사용자별 구분이 없기 때문에 다른 사람이 접속하더라도 동일한 데이터를 조회하거나, 정책이 허용하는 범위에서 다른 사람의 일기를 삭제할 수 있습니다.

이를 개선하려면 Supabase Auth를 이용한 로그인 기능을 추가하고, `user_id` 컬럼을 만들어 각 일기의 작성자를 구분해야 합니다. 이후 RLS 정책을 이용해 로그인한 사용자 본인의 데이터만 조회, 추가, 수정 및 삭제할 수 있도록 제한해야 합니다.

이번 실습을 통해 API 키를 숨기는 것만큼이나 실제 데이터베이스의 접근 권한을 올바르게 설정하는 것이 중요하다는 점을 알게 되었습니다.

## 커스터마이징한 부분

기본적인 일기 작성 및 조회 기능 외에도 사용하기 편리하도록 몇 가지 요소를 추가하고 수정했습니다.

1. **감정별 디자인:** 감정에 따라 서로 다른 이모지를 표시하여 일기 목록을 직관적으로 확인할 수 있도록 했습니다.
2. **감정 필터:** 전체 일기를 확인하는 기능뿐 아니라 특정 감정으로 작성한 일기만 모아서 볼 수 있도록 했습니다.
3. **삭제 확인 창:** 실수로 일기를 삭제하는 것을 방지하기 위해 삭제 전에 확인 창이 나타나도록 했습니다.
4. **반응형 디자인:** 스마트폰과 PC 등 다양한 화면 크기에서도 편리하게 사용할 수 있도록 Tailwind CSS를 활용했습니다.
5. **상태 안내:** 데이터를 불러오는 중에는 로딩 표시를 보여주고, 저장 중에는 버튼을 비활성화해 중복 저장을 방지하도록 했습니다.
6. **빈 목록 안내:** 작성된 일기가 없거나 선택한 감정에 해당하는 기록이 없을 때 안내 문구를 표시하도록 했습니다.
7. **오류 안내:** 네트워크 연결이나 Supabase 인증 및 데이터베이스 접근 과정에서 오류가 발생하면 사용자에게 오류 메시지를 표시하도록 했습니다.

이번 프로젝트를 통해 단순히 브라우저에 데이터를 저장하는 방식에서 벗어나 외부 데이터베이스를 이용한 웹 애플리케이션을 구현하는 과정을 경험할 수 있었습니다.
